# board_t1_cmake

This is the **baseline** project of the `board_t1/` board. It lives at
`board_t1/board_t1_cmake/` and is the source of the generated/peripheral infrastructure
(rebuilt from `board_t1/board_t1.ioc2`). Sibling projects (`coremark_144m`,
`dhry_144m`) reuse this baseline's files via relative paths.

Bare-metal STM32C542RCT6 project (Cortex-M33) generated by CMSIS-Toolbox / STM32CubeMX2,
built with a CMake + Ninja toolchain. Two reproducible build configurations are supported
(details below): **release_GCC** and **release_ARMCLANG** (ST LLVM).

## Overview

- MCU: **STM32C542RCT6** (Cortex-M33, 144 MHz, 256 KB flash, 128 KB RAM)
- Board: **NUCLEO-C542RC**
- Build system: CMake (Ninja generator)
- Toolchains:
  - **Arm GCC 14.3.1** (`D:\arm-none-eabi-tc\bin`) — `release_GCC`
  - **ST LLVM** (`starm-clang`, from STM32CubeIDE) — `release_ARMCLANG`
- Debug probe: on-board ST-Link (V3)

### What the firmware does (`main.c`)

On each 100 ms tick:

1. **LD1 (PA5) toggles every 500 ms.** PA5 is configured as an open-drain output,
   **active-low** (pin low = LED on, pin high = LED off), init state = reset (on).
2. **System clock printed every 5 seconds** over USART2:
   `SystemCoreClock = 144000000 Hz`

UART output is retargeted to **USART2** (PA2=TX, PA3=RX) at **115200 baud, 8N1** via
`retarget.c` (a strong `_write` that overrides the weak stub in
`utilities/syscalls/syscalls.c`). The ST-Link Virtual COM Port maps to the on-board VCP.

## Toolchain

Tool paths are pinned (rather than guessed) via `bootstrap.ps1`, which is the recommended
way to set up the environment. The reference tools are bundled with **STM32CubeIDE 2.1.1**:

| Tool | Path |
|------|------|
| Bash   | `C:\msys64\usr\bin\bash.exe` |
| CMake  | `.../com.st.stm32cube.ide.mcu.externaltools.cmake.win32_*/tools/bin/cmake.exe` (4.3.1) |
| Ninja  | `.../com.st.stm32cube.ide.mcu.externaltools.ninja.win32_*/tools/bin/ninja.exe` |
| GCC    | `D:\arm-none-eabi-tc\bin\` (or STM32CubeIDE bundled `gnu-tools-for-stm32`) |
| ST LLVM| `.../com.st.stm32cube.ide.mcu.externaltools.llvm.win32_*/tools/bin/` (`starm-clang`) |
| Programmer | `D:\Program Files\STMicroelectronics\STM32Cube\STM32CubeProgrammer\bin\STM32_Programmer_CLI.exe` |

> If you only have the system `cmake` (3.20.5), note it cannot read `CMakePresets.json`
> version 3. Use CMake >= 3.21 (e.g. the STM32CubeIDE-bundled 4.3.1, or
> `C:\Users\user1\.mcuxpressotools\cmake-3.30.0\bin\cmake.exe`).

| Preset (configure) | Build dir | Compiler | C library |
|------|------|------|------|
| `release_GCC_NUCLEO-C542RC` | `build\release_GCC_NUCLEO-C542RC` | Arm GCC 14.3.1 `-O2` | newlib-nano |

Each config is a separate build directory, so they can coexist.

## Build, flash, capture

Set up the environment once (from `board_t1_cmake/`):

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File bootstrap.ps1
```

This puts the STM32CubeIDE CMake/Ninja/GCC on `PATH` (and, for the ARMCLANG preset, the
ST LLVM `bin`), so the plain commands below work. It also discovers the ST-Link VCP COM port.

Configure once (from the project root):

```bat
cmake --preset release_ARMCLANG_NUCLEO-C542RC    :: or release_GCC_...
```

All subsequent commands are Ninja targets, run **from the matching build directory**:

```bat
cd build\release_ARMCLANG_NUCLEO-C542RC

ninja            :: build the ELF      (board_t1.elf)
ninja hex        :: build Intel HEX    (board_t1.hex)
ninja flash      :: program the MCU via STM32CubeProgrammer (SWD, under-reset, verify, reset)
ninja capture    :: capture UART output from the ST-Link VCP and print it live
```

Swap the build dir for the config you want (e.g. `build\release_GCC_NUCLEO-C542RC`).

### Outputs

- `build\<config>\board_t1.elf`
- `build\<config>\board_t1.hex`
- `build\<config>\board_t1.map`

where `<config>` is one of the two build-dir names above.

### Flash

`ninja flash` uses `STM32_Programmer_CLI.exe` with:

```bat
STM32_Programmer_CLI.exe -c port=SWD mode=UR -w board_t1.elf -v -rst
```

`mode=UR` connects under reset (robust on NUCLEO boards), verifies the download, and
resets the MCU so it runs immediately.

### Capture / verify

`ninja capture` opens the ST-Link Virtual COM Port (auto-detected; on this machine
**COM73**) at 115200 baud and prints received lines live. It also appends to a log file
if `-LogFile` is given.

COM-port override (the port number can change):

```bat
ninja capture                                    :: auto-detect COM
SERIAL_PORT=COM73 ninja capture                  :: force the port (PowerShell)
set SERIAL_PORT=COM73 && ninja capture           :: force the port (cmd)
```

Or run the script directly:

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File capture.ps1 -Port COM73 -LogFile uart.log
```

You should see (every 5 seconds):

```
SystemCoreClock = 144000000 Hz
```

and LD1 blinking at ~2 Hz. This confirms both the clock reporting and the LED toggle.

## About the ARMCLANG (ST LLVM) configuration

The `release_ARMCLANG` preset uses ST's LLVM-based compiler (`starm-clang`, target
`arm-st-none-eabi`) instead of Arm GCC. Because ST clang defaults to the **picolibc**
runtime while this project's generated startup/syscall code is newlib-flavoured, the
toolchain file (`cmake/STLLVM.cmake`) selects the ST-bundled **newlib** runtime instead:

- **Runtime selection** by path is done in `STLLVM.cmake`: it points the C/C++ standard
  library search path at `.../tools/lib/clang-runtimes/newlib/arm-none-eabi/<triplet>`.
- **Linking** uses `-nostdlib` plus the explicit newlib archives
  `libcrt0-nosys.a` (provides `_start`), `libc.a`, `libm.a`, `libnosys.a` (syscall
  stubs) and `libclang_rt.builtins.a`, wrapped in `--start-group`. They are linked by
  **absolute path** rather than `-L/-l`, because the ST clang driver mishandles
  `-L <path>` when split across command-line tokens.
- **Stack symbols** (`__stack`, `__stack_limit`) must be real linker-script symbols, not C
  variables. The CMSIS clang header (`cmsis_clang_m.h`) maps `__INITIAL_SP`→`__stack` and
  `__STACK_LIMIT`→`__stack_limit`, and `Reset_Handler` programs them into the M33
  `MSPLIM`/`PSPLIM`/PSP registers. So the linker script `stm32c542xc_flash.ld` defines
  both (`__stack = __StackTop; __stack_limit = __StackLimit;`). Defining `__stack_limit`
  as a C `const` variable instead puts a flash address into MSPLIM and crashes at reset.
- `armclang_runtime.c` is a small CLANG-only shim that supplies `__aeabi_read_tp`
  (newlib's per-thread TLS base, needed if a newlib path uses thread-local errno).
- `crt0_clang.c` is a CLANG-only shim providing a strong `_start`/`_mainCRTStartup`
  that copies `.data` and zeroes `.bss` (the ST newlib crt0 leaves its data-copy hook
  NULL, so without this the board would not boot under ST LLVM) plus a `_sbrk` that
  stops at `__HeapLimit` instead of growing the heap into the stack.
  Both shims are only compiled for the CLANG family.
- The DFP "Standalone syscalls/sysmem" sources are excluded for CLANG
  (`components.cmake`); the newlib `libnosys.a` supplies the syscall stubs instead.

The `__aeabi_read_tp` shim and the `__stack`/`__stack_limit` linker-script symbols only
exist (and are only relevant) for the ARMCLANG build, which is why they are gated on the
CLANG compiler family / kept in the script noted above.

## Why openocd / probe-rs are NOT provided

Both were checked for STM32C5 support; neither can program the C542 with the installed
versions, so no `ninja flash-ocd` / `ninja flash-pr` targets are created.

- **openocd** (`xpack-openocd-0.12.0-7`): ships no `stm32c5x.cfg`. The closest,
  `stm32x5x_common.cfg`, targets the **STM32L5/U3/U5** families (different flash
  controller, register map, and RDP/TrustZone option layout) and would use the wrong
  `stm32l4x` flash driver for the C5.
- **probe-rs** (`0.32.0`): its chip database contains **no STM32C5 series**, so it has no
  target definition/flashing algorithm for the C542.

STM32CubeProgrammer fully supports the STM32C5 (verified above) and is the recommended
flashing path.

## Project layout

Key files: `CMakeLists.txt` (entry), `CMakePresets.json` (release_GCC /
release_ARMCLANG), `bootstrap.ps1` (tool-path setup), `main.c`/`main.h` (LED toggle +
clock print + internal ADC sampling), `adc_internal.c`/`adc_internal.h` (samples the
ADC1 internal channels: die temperature in °C and VREFINT in mV), `retarget.c`
(printf → USART2), `capture.ps1` (UART capture),
`armclang_runtime.c` + `crt0_clang.c` (CLANG-only shims), `cmake/` (build modules),
`generated/hal/`
(HAL init/config), `stm32c5xx_dfp/`, `stm32c5xx_drivers/`, `user_modifiable/` (startup,
system, linker script), `utilities/syscalls/` (newlib stubs — GCC only), `arch/cmsis/`.

## Regenerating from the .ioc2

The source of truth is `board_t1.ioc2` in the `board_t1/` folder; re-run the CMSIS-Toolbox /
STM32CubeMX2 code generation to regenerate this project. Hand-written files
(`main.c`, `retarget.c`, `capture.ps1`, `cmake/tools.cmake`) may need to be re-applied
after regeneration.
